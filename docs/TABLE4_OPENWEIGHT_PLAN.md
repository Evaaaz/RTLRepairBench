## 3. Two findings that should shape the decision

### 3.1 The open-weight rows are on a different prompt grammar from the rest of Table 4

This is not documented in the caption and I think it matters more than the
dashes do.

- Rows for gpt-5.5, Claude 4.8, gpt-4.1, gpt-4o-mini, llama-3.3-70b and
  OriGen_Fix come from the **main85 2×2 grid** — `prompts.spec_locate_prompt`,
  arms `spec0_loc0 … spec1_loc1`. The baseline is a true *no-signal* arm: buggy
  module, nothing else.
- Rows for base/v5/verireason/vrqwen come from the **RepairBench `diag`
  grammar** — `repair_agent._build_prompt`, every arm carries a tool
  diagnostic. Their "no-signal baseline" column is really the
  tool-diagnostic arm.

The case sets *are* the same (verified: main85's 52 seeds and the 85 semantic
held-out cases are the identical set), so the columns are comparable in cohort
but not in prompt. A Where cell added under the `diag` grammar inherits the
mismatch; adding it under the main85 grammar means re-running the baseline and
What cells too, which changes three published numbers per row.

### 3.2 Where cannot be honestly reported at Tier S

The paper's own Appendix C measures this: rescoring the frozen candidates with
the reset-aware simulator instead of the proof moves **What by +0.8pp but Where
by +7.4pp** (proof says `0.0`, simulation says `+7.4`). Section 5.3 finds the
same asymmetry on these very open-weight candidates — Tier F moves the spec
arms down four times harder than the diagnostic arms.

Bounded simulation is biased *toward* making localization look helpful, and the
paper's claim is that localization is null. A Tier S Where column would be
biased in exactly the direction that undercuts the thesis, by more than the
effect being measured. **Where needs Tier F.**

Counterexample is different: the three existing CE cells are already
`scored_by: differential_simulation` (see
`generated/counterexample/*/result.json`). A Tier S CE cell for the open-weight
models is consistent with what is already published.

## 4. The blocker — and why it is a toolchain blocker, not a Docker one

What Tier F needs is **eight binaries**: `yosys`, `sby`, `abc`, `z3`,
`boolector`, `iverilog`, `vvp`, `verilator` (`docker/formal/toolchain.lock.json`,
`required_tools`). This host has only `iverilog`, `vvp` and `verilator`.
`run_validation_batch` hard-checks Icarus and shells out to the rest, so the
missing formal engines are the actual blocker.

Docker is how the repo *ships* those eight, not something the code requires. It
buys two specific things:

1. **Pinned identity.** The lock pins the Ubuntu 24.04 OCI digest and the OSS
   CAD Suite `2026-05-08` tarball SHA — but only for `linux-arm64` and
   `linux-x64`. There is no darwin asset in the lock, so any native macOS
   install is outside it.
2. **Provenance stamping.** `formal_protocol_fingerprint()`
   (`formal_verify.py:120`) folds `$RTLREPAIR_FORMAL_IMAGE_ID` into the
   `formal_protocol_sha256` written onto every verdict. Outside the container it
   hashes the literal string `"no-container-id"`.

### The existing open-weight Tier F rows were produced without the container

All 680 rows in `generated/tierf_openweight/results.jsonl` carry
`formal_protocol_sha256 = 0efba7ab05f6…`. Running
`formal_protocol_fingerprint()` on this host with no image id set reproduces
that hash **exactly** — it is the no-container value. The collaborator who
produced them (their macOS home directory appears in the recorded yosys
commands) had the full suite installed natively; the engine mix proves it:

```
smtbmc-bmc256        368     abc-pdr          131     yosys-sat-exhaustive  132
```

`abc-pdr` and `smtbmc-bmc256` are the sby/ABC/SMT backends — not something a
partial install produces.

By contrast the **primary, preregistered** Tier F *did* run in the container:
`artifacts/public/primary/manifests/06_toolchain_manifest.json` records
`container_image: rtlrepair-formal:20260508`, image id `sha256:d2065a4f…`,
platform `Linux-…-aarch64`. That run is what the Appendix F verifier audit is
bound to.

### What this means for the Where cells

Matching the row they join argues for a **host toolchain, not the container**.
The baseline and What cells for these four models carry the `0efba7ab…`
fingerprint; a containerised Where cell would carry a different one, putting
three cells of one row on two protocol identities. So:

| route | tools | fingerprint | note |
|---|---|---|---|
| collaborator handoff | already there | matches the banked 680 | zero setup, strongest consistency |
| native OSS CAD Suite here | manual install | matches the banked 680 | outside the lock file's pinned assets |
| colima + docker | pinned, one command | differs from the banked 680 | matches the *primary* run instead |

```bash
# only if the container route is chosen
brew install colima docker && colima start --cpu 4 --memory 8
code/scripts/run_formal_container.sh --build toolchain-info \
  --output generated/formal/toolchain_manifest.json
```

### Running it natively on this Mac

Nothing in the verifier is Linux-specific, and **tool versions are recorded,
never enforced** — `collect_toolchain_manifest` (`formal_verify.py:210`) probes
PATH and writes what it finds. So the native route is purely "put eight
binaries on PATH". Current state here (`formal_verify.py toolchain-info`,
runs fine outside the container):

```
platform macOS-26.5.2-arm64      iverilog OK 13.0   verilator OK 5.048   vvp OK 13.0
                                 yosys MISSING  sby MISSING  abc MISSING  z3 MISSING  boolector MISSING
```

Closest match to the audited container is the OSS CAD Suite **darwin-arm64**
build of the same `2026-05-08` release — one tarball carrying all eight, same
upstream as the `/opt/oss-cad-suite/bin/*` paths in the image manifest. Two
caveats: `toolchain.lock.json` pins SHAs for `linux-arm64`/`linux-x64` only, so
a darwin asset is outside the lock and we should record its SHA ourselves; and
macOS quarantine has to be cleared on the unpacked binaries. Note the OSS CAD
Suite would also supersede the host Icarus (13.0 stable vs the container's 14.0
devel) and Verilator (5.048 vs 5.049-mod) for the duration of the run.

**Gap worth closing either way:** there is no toolchain manifest anywhere in
the tree for the Mac that produced the banked 680 — the only manifests are the
container's. We cannot currently state which tool versions produced the
published open-weight Tier F numbers. Whoever runs Phase 3 should write
`toolchain-info` output alongside the results first; that is a one-command fix
and gives the new cells provenance the existing ones lack.

| column | needs Modal | needs container |
|---|---|---|
| Counterexample | yes | **no** — witnesses banked, scored by sim |
| Where | yes | **yes**, to be credible |

## 5. Proposed plan

### Phase 0 — decisions (blocking, for review)

- **D1. Which grammar for Where?**
  - *A — main85 grid (recommended).* Run `spec0_loc0`, `spec0_loc1`, `spec1_loc0`
    on all four models; the whole open-weight block moves onto the same prompt
    as every other row and §3.1 stops being a hidden caveat. 85 × 3 × 4 =
    **1,020 calls**. Costs three changed numbers per row.
  - *B — `diag_locate`.* Where relative to the existing diag baseline.
    85 × 4 = **340 calls**, no published number changes, §3.1 stays and has to
    be stated in the caption.
- **D2. Tier F toolchain: collaborator handoff, native install here, or the
  container?** See §4 — this is a choice about which protocol fingerprint the
  new cells carry, not about whether the code runs. Nothing else on the
  critical path is blocked by it.
- **D3. Counterexample go/no-go.** Cheap, unblocked, and gives cohorts of
  57–71 against the current 39–50 — the strongest power any CE row would have.

### Phase 1 — Counterexample (unblocked, ~1 day)

1. Extend `code/scripts/x1_counterexample_power.py` to read the open-weight
   run tree. Two concrete changes:
   - selection: it currently reads `generated/second_model/{verdicts.jsonl,results.json}`
     and filters `arm == "spec0_loc0"`. Needs a path that filters
     `generated/tierf_openweight/results.jsonl` on
     `formal_verdict.verdict == "COUNTEREXAMPLE"` for `<model>__diag`.
   - witness: `formal_witness()` reads sby's `run/engine_0/trace_aiw.yw`, which
     the yosys-`sat` runs did not produce. Add a reader for
     `formal/replay/witness.json` (`input_trace` + `first_divergence` — same
     information, already replayed under Icarus). Without it every case silently
     falls through to `sim_witness`, which is a weaker arm than the one the
     other three rows got.
2. Deploy each Modal app, run concrete + generic revisions:
   251 refuted cases × 2 arms = **502 calls**.
3. Score with `reset_aware_sim`, exact McNemar — unchanged from the existing
   path. Bank under `generated/counterexample/<model>/`.

### Phase 2 — Where generations (unblocked, ~1 day)

Per D1. Under option A, per model:

```bash
export RTLREPAIR_LLM_URL=https://<modal-app>.modal.run/v1
export RTLREPAIR_LLM_API_KEY=<key>
python code/benchmarks/generate_ledger.py --model <id> \
  --arms spec0_loc0,spec0_loc1,spec1_loc0 --workers 8 --bank
```

Under option B, `--bench --bucket semantic --arms diag_locate` instead. Watch
the `had_locate` warning it prints — it is empty when no golden is on disk;
all 85 semantic cases have one, so it should report zero.

No container needed for this phase. Ledgers are banked with candidate RTL, so
Phase 3 is a rescore, not a regeneration.

### Phase 3 — Tier F scoring (blocked on D2, ~30 min of compute)

1. Get the eight tools onto whichever machine D2 selects (§4), and capture a
   `toolchain-info` manifest before scoring anything.
2. Build `jobs.jsonl` from the new ledgers in the shape
   `run_validation_batch` takes (`formal_verify.py:1679`):
   `{call_id: "<model>__<arm>__<case_id>", seed_id, golden_rtl, candidate_rtl}`.
   `call_id` must carry the arm — `case_id` is unique only within an arm.
3. Run resumably; 340 jobs (option B) or 680 (option A). **This is fast** — the
   banked 680 took 12 minutes of solver time in total (median 1.1 s/job, max
   32 s; `smtbmc-bmc256` dominates at 8.3 min of the 12). Budget under an hour
   wall clock including Icarus replay, not the "few hours" earlier notes
   assumed. Expect 91% definitive: of the banked 680, 62 came back
   `UNSUPPORTED` and 5 `COMPILE_FAIL`, so 2–14 cases per arm fall back to
   Tier S.

### Phase 4 — regenerate the table

`e6_decomposition_table.py` currently hardcodes `"---"` for these cells and
reads `generated/tierf_openweight/what_effects.json`. It needs a Where and CE
source per open-weight model plus a Holm family that widens from 1 to 3
contrasts on those rows. Caption edits: drop "the open-weight models have no
localization arm", update the CE sentence's pooled n, and — under option B —
state the grammar split from §3.1 explicitly.

## 6. Cost and effort

| item | scale | cost |
|---|---|---|
| Modal, 4 × L40S @ $1.95/hr | ~30 min each incl. cold start | **~$4–8 total** |
| calls | 502 (CE) + 340 or 1,020 (Where) | tokens are on our own endpoints |
| formal toolchain | one-time, per §4 | free, ~20 min (or zero on handoff) |
| Tier F compute | 340–680 jobs, resumable | ~12 min solver, under an hour wall clock |

Cold starts dominate GPU time, not the calls — banked median latency is
6.5–11 s/call, so 85 cases at `--workers 8` is 1–2 min of serving. First-ever
boot per app is 10–20 min while the weights download into the Modal volume;
later boots are 2–4 min. Set the workspace spend limit before deploying.

## 7. What I would do

Phase 1 regardless — it is cheap, needs no formal toolchain at all, has the
banked witnesses sitting there, and would give the Counterexample column its
four best-powered rows. Then D1 as option A.

On D2, a native OSS CAD Suite install on this Mac and the collaborator handoff
are equivalent on the thing that matters — both stamp the no-container
fingerprint the existing cells carry — so it comes down to whether we want the
tools here. Given the solver cost is 12 minutes, installing locally buys
control over the schedule and removes a coordination dependency; the handoff
buys not installing anything. Standing up colima is the *worse* option for
these particular rows, which is the opposite of what I said in the first draft
of this plan.

I would not ship a Tier S Where column. Per §3.2 it is biased by more than the
effect, in the direction that contradicts the paper's own claim, and a dash
that the caption explains is a better exhibit than a number we would have to
argue against.

## 8. What was actually run, and where this plan was wrong

Executed 2026-08-08. Option B (`diag_locate` against the banked `diag`
baseline), because the brief was to fill blank cells rather than restate
published ones. 842 model calls, no failures.

| step | result |
|---|---|
| Where generations | 340 calls, 4 models x 85 cases, 0 errors |
| Counterexample | 502 calls over 251 refuted baselines, 0 errors, 251/251 paired |
| Tier F scoring | 339 jobs, ~7 min wall clock, 76-82 of 85 definitive per arm |

**Where** (Tier F): base $-6.5$ $[-16.3,+3.3]$, v5 $+1.7$ $[-10.3,+13.3]$,
VeriReason $+18.5$ $[+5.9,+31.1]$, VR-Qwen $+2.9$ $[-6.4,+12.4]$.
**Counterexample** (Tier S, as the published rows): $+1.8$, $-1.7$, $-1.6$,
$+0.0$; all $p{=}1.0$, on cohorts of 57-71 against the published rows' 39-50.

Five things this plan got wrong or missed:

1. **§3.2's argument indicts a cell already in the table.** Claude Opus 4.8's
   Where is `scored_by: differential_simulation` — the exact tier the $+7.4$pp
   bias was measured on. The Where column mixes tiers; the caption now says so.
2. **The caption's Holm claim was never implemented.** `e6_decomposition_table.py`
   computes no statistics at all, and no Holm correction exists on that path.
   Rather than widen the preregistered row's published intervals, the caption now
   states what is true: frozen family corrected upstream, exploratory rows not.
3. **The open-weight cells had no producer.** `what_effects.json` and
   `openweight_tier_f.json` were orphan JSON — nothing in the tree could
   re-derive or check them. `e7_openweight_decomposition.py` now does, and
   self-checks against the published What effects.
4. **Phase 2 predicted the `had_locate` warning would report zero. It reported
   2/85.** `buggy_line` returns None when the mutated line recurs verbatim in the
   golden, silently making those cases duplicates of the baseline arm and biasing
   Where toward null. `generate_ledger.py` now falls back to the grid's oracle.
   Where both are available they agree on all 83.
5. **§4's fingerprint argument is weaker than stated.** `formal_protocol_fingerprint()`
   hashes source and the lock file, not installed binaries, so a matching
   fingerprint says nothing about solver versions. Checked separately instead:
   the installed suite reports the same upstream release and git SHAs as the
   container manifest (yosys `0.64+199 bfc09777e`, sby `v0.64-2-gf57802a`,
   z3 `4.15.5`, boolector `3.2.4`), differing only in host triple. The manifest
   is banked at `generated/tierf_openweight/toolchain_manifest_diag_locate.json`,
   which is the record the banked 680 never got.

## 9. OriGen_Fix follow-up

Done in a second pass. The `origen-vllm` Modal app was deployed and OriGen_Fix
run on three fronts; only Claude Opus 4.8 now keeps a dashed Counterexample cell.

* **Counterexample** `+0.0`pp, n=55, p=1.0. Its grid work dirs were never
  retained (neither were llama's), so the failing baseline the arm revises did
  not exist. Rather than regenerate a grid baseline under OriGen's bespoke
  local-inference prompt, its counterexample is footed on its `diag` arm and Tier F
  scored (55 refuted of 81 definitive), which is the identical pipeline the other
  four open-weight rows use.
* **Recovery table.** OriGen was absent from `tab:recovery` entirely. Added:
  diagnostic 90.6% lint / 31.8% semantic, diagnostic+spec 87.7% / 29.4%. The
  scoring pipeline reproduces all eight published cells of that table exactly,
  including the v5-vs-base p=0.83, so the new rows are directly comparable.
* **Specialization panel.** The prose claimed *four* RTL-specialized models and
  `tab:special` listed three; OriGen_Fix is the missing "repair-specific LoRA".
  Added below a rule with a footnote, because it postdates that batched run and
  is not comparable down the column.

**The claim that had to change.** OriGen scores 31.8% semantic against the base's
25.9% -- it *beats* the untuned base by +5.9pp, though only at p=0.41 (exact
McNemar, n=85). "All fail to beat an untuned general-purpose base" and "None
beats" were therefore false as written. Both now say none *significantly* beats,
and state OriGen's positive point estimate outright. Note this is also the one
panel model whose native interface is repair rather than generation.
